# AIPulse 资讯获取与热点发现需求调研文档

> 版本：v0.1
> 日期：2026-07-25
> 状态：调研结论
> 调研对象：NewsNow、TrendRadar，以及 AIPulse 当前热点监控实现

## 1. 文档目的

本文档把 NewsNow 的多源信息聚合能力与 TrendRadar 的热点筛选、趋势分析能力，转化为符合 AIPulse 定位的产品需求。目标不是复制任一上游项目，而是在 AIPulse 既有 `Source → Collector → Hotspot → Digest` 链路上补齐可持续的信息输入和用户消费闭环。

AIPulse 的核心差异是：信息不是终点，而是后续 AI 摘要、视频/文章处理、Obsidian 归档、学习事件和通知的输入。因此本需求优先考虑本地优先、可追溯、可归档和可扩展，而不是单纯做一个热榜展示站。

## 2. 调研结论摘要

| 项目 | 核心能力 | 对 AIPulse 的结论 |
|---|---|---|
| NewsNow | 多平台源适配、分源刷新间隔、两级 TTL 缓存、旧缓存降级、RSS/HTML/API 统一接入 | 借鉴适配器和缓存思想；不直接迁移其 Nuxt 3/Nitro + Vue 3 前端和服务端框架 |
| TrendRadar | 通过可配置的 NewsNow API 部署获取热榜，维护排名历史，按关键词/AI 兴趣筛选，按时段执行分析和推送，多渠道通知 | 借鉴数据模型、报告模式和调度模型；运行时不依赖其默认第三方 NewsNow 地址；GPL-3.0 源码不直接并入 AIPulse |
| AIPulse | 已有 Collector 注册、热点评分、LLM 分析、关键词 CRUD、日报、SSE、Obsidian 归档和通知基础 | 以现有 Python sidecar/FastAPI/SQLite 为主，不新增独立聚合服务 |

## 3. 用户与核心场景

### 3.1 目标用户

- AI 从业者、研究者、开发者和技术观察者；
- 需要持续追踪指定主题并沉淀知识的内容创作者；
- 希望把“看到热点”直接转化为摘要、任务或 Obsidian 笔记的个人用户。

### 3.2 核心用户故事

| 编号 | 用户故事 | 优先级 |
|---|---|---|
| US-01 | 用户打开 Dashboard 后能看到来自多个来源、按新鲜度和相关性排序的信息流 | P0 |
| US-02 | 用户可按来源、分类、时间、重要性和关键词筛选热点 | P0 |
| US-03 | 用户配置关键词后，命中内容被标记、加权，并可选择触发通知 | P0 |
| US-04 | 同一事件来自多个平台时，用户能看到聚合关系，而非重复卡片 | P1 |
| US-05 | 用户能查看一个热点的来源、排名变化、摘要和相关热点 | P1 |
| US-06 | 用户可将热点送入现有文章/视频摘要和 Obsidian 归档流程 | P1 |
| US-07 | 用户每天能查看一份按主题组织的 AI 热点日报 | P1 |
| US-08 | 用户能看到数据源的最近成功时间、失败原因和健康状态 | P1 |
| US-09 | 用户可添加 RSS 等低风险自定义来源 | P2 |
| US-10 | 用户可配置采集、分析、通知的时间段，避免夜间无意义处理 | P2 |

## 4. 产品范围

### 4.1 本阶段必须包含

1. 多源资讯/热榜采集：沿用 AIPulse Collector Registry，覆盖现有 RSS、GitHub、arXiv、Bilibili、知乎、微博、百度、V2EX 等可验证来源。
2. 分源刷新：每个 Source 可配置刷新间隔、最大内容年龄和启用状态。
3. 统一规范化：所有输入转换为统一候选结构，保留来源、原始 URL、发布时间、排名和可用互动指标。
4. 可靠缓存：按来源缓存，采集失败时返回最近成功数据，并记录错误状态。
5. 热点处理：URL 规范化去重、关键词匹配、LLM/规则分析、热度计算、持久化和 SSE 推送。
6. 信息流 Dashboard：分页、搜索、来源/分类/重要性/时间筛选，展示新热点和来源状态。
7. 关键词闭环：关键词 CRUD、命中记录、热度加权、通知开关和筛选。
8. 日报闭环：沿用 DailyDigest，聚合最近窗口内的高价值热点，支持 Web 展示和现有通知渠道。

### 4.2 后续阶段包含

- 多来源事件聚类和排名时间线；
- AI 自然语言兴趣筛选；
- 多渠道通知渲染器；
- 自定义 RSS 管理；
- 时段化采集/分析/推送策略；
- MCP 查询工具；
- 关联 followed-up、学习事件和知识库查漏补缺。

### 4.3 明确不做

- 不直接复制 TrendRadar GPL-3.0 源码；
- 不把 NewsNow 的 Nuxt/Nitro 前端和独立用户系统并入 AIPulse；
- 不默认使用需要登录 Cookie、绕过风控或高频抓取的来源；
- 不在第一阶段存储第三方文章全文；
- 不把热度分数当作事实真实性或投资/决策建议；
- 不为追求“实时”引入常驻浏览器池或代理池。

## 5. 功能需求

### 5.1 数据源管理

- 当前 Source 已支持名称、类型、Collector、配置、权重、刷新间隔和启用状态；最近成功时间、连续失败次数、健康状态、最大年龄等展示或控制字段属于本需求的新增/补强范围。
- 支持单源立即同步；单个来源失败不得阻断其他来源。
- Collector 必须通过 `BaseCollector.fetch()` 和 `normalize()` 接入，并通过 Registry 注册。
- 配置中的端点、Cookie、Token 等敏感信息必须进入统一 secret 管理，不得进入普通 JSON 返回值。

### 5.2 采集与缓存

- 当前调度器为统一 30 分钟轮询；目标是 Phase 1 改为 Source 级 next-run 判断：高频来源 10—15 分钟，普通来源 30—60 分钟，低频来源 6—24 小时。
- 缓存至少支持“来源刷新间隔”和“最大缓存存活期”两个概念。
- 采集成功写入原始更新时间和规范化条目；失败保留旧数据并产生可观测错误。
- 每个来源必须限制单次条目数、请求超时和重试次数；不得无限重试。
- RSS 源按发布时间和最大年龄过滤；榜单源保留原始 rank。

### 5.3 热点处理与去重

- URL 规范化后以 `canonical_url` 做第一层去重。
- 标题短、URL 缺失或跨平台转载场景不得只依赖标题作为全局唯一 ID。
- 第二阶段再启用标题相似度/事件聚类；聚类必须保留每个来源链接和原始排名。
- LLM 不可用时，规则分析仍应允许内容进入信息流，并将分析置信度标记为降级状态。
- 热点状态、摘要、分类、重要性和分析错误必须可追溯。

### 5.4 关键词与兴趣

- 关键词支持启用/停用和 `notify_on_match`。
- 第一阶段支持标题 + 摘要的大小写无关字面匹配，并记录命中的关键词。
- 关键词影响排序和筛选，不得单独决定内容真实性。
- 后续可增加必含词、普通词、排除词和别名，但需保持向后兼容的数据模型。
- AI 兴趣筛选属于增强能力，必须保留确定性关键词匹配作为可解释回退。

### 5.5 热度与趋势

- 热度由来源权重、互动指标、关键词匹配、多源出现、新鲜度和质量组成。
- 来源没有真实互动指标时，不得用虚构数值伪装热度；应按排名、出现频次和来源权重计算可解释分数。
- 新鲜度半衰期必须按内容类型配置。现有约 3 分钟的默认衰减不适合作为所有 RSS/论文内容的统一策略，实施前需以历史数据校准。
- 排名变化、跨源出现次数和历史轨迹属于趋势指标，不等同于事件热度事实。

### 5.6 信息消费与后续动作

- 信息流卡片至少展示标题、来源、时间、重要性、摘要、关键词命中和原文链接。
- 支持“打开原文”“加入处理任务”“归档到 Obsidian”三个动作；后两者复用既有 pipeline。
- 新热点通过 `/api/sse/hotspots` 推送，断线后客户端必须重新拉取分页数据而非依赖事件补全历史。
- 日报应引用已存热点和原文链接，失败时保留生成错误状态，不生成空白成功日报。

## 6. 验收标准

### P0

1. 首次完成配置后，至少 5 个来源能成功同步并在 5 分钟内产生可展示条目。
2. 单个来源超时或解析失败时，其余来源仍完成同步，来源状态可见。
3. 用户新增关键词后，新匹配热点能在列表中显示命中标记，并按配置参与排序。
4. 相同 canonical URL 不会重复创建；采集失败时最近成功数据仍可读取。
5. Dashboard 支持分页、来源、分类、重要性、时间和关键词筛选。
6. 新热点可通过 SSE 到达，断线重连后不重复创建。

### P1

1. 一个事件的多源条目可关联查看，保留每个来源和排名。
2. 热点可进入现有摘要/归档流程，任务失败状态可回写。
3. 每日报告可查看历史记录，并能通过已有通知渠道发送。
4. 来源连续失败达到阈值后，Phase 1 新增的健康状态字段变为 degraded 并产生通知。

### P2

1. 用户可配置时段化 collect/analyze/push 行为。
2. 支持自然语言兴趣筛选和趋势图。
3. 支持自定义 RSS 和 MCP 查询。

## 7. 关键产品决策

- **单一事实源**：AIPulse 的 `hotspots` 是信息流事实存储；NewsNow/TrendRadar 不作为运行时必需依赖。
- **本地优先**：采集、缓存、关键词、日报和通知决策默认在 Python sidecar/本地数据库完成。
- **渐进增强**：先用规则和明确指标保证信息可见，再用 LLM 做摘要、分类和筛选。
- **可解释优先**：列表排序必须能解释来源权重、关键词命中、新鲜度和跨源次数。
- **合规优先**：公开 API/RSS 优先；每个新源在上线前记录 Terms、robots、频率限制和再分发边界。

## 8. 风险与产品约束

| 风险 | 约束/应对 |
|---|---|
| 平台 API 或页面变更 | Collector 独立隔离、健康状态、旧缓存降级、单源手动重试 |
| 反爬与限流 | 公开接口优先、分源频率、超时/退避；不默认代理池和登录 Cookie |
| 数据再分发 | 默认只保存标题、摘要、指标和原文链接；逐源确认条款 |
| TrendRadar GPL-3.0 | 只参考架构/数学模型/配置思想，不复制源码或形成派生模块 |
| 热度误导 | 展示指标来源和更新时间；热度不等于真实性或价值判断 |
| LLM 成本与延迟 | 先规则入库，批量/异步分析，失败降级，不阻塞采集 |
| 本地数据库增长 | 条目保留期、索引、日报归档和清理策略纳入技术实现 |
